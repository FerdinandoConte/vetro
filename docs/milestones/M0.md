# M0 — Baseline and feasibility (before any product code)

**Goal:** know the real numbers and the real constraints of the reference hardware before writing the engine, so M1 is planned on facts.

## Exit criteria
Every box checked, each with a file or issue as evidence:
- [ ] Dev environment builds a Rust MSVC binary, an Android `arm64-v8a` library, and lists `hevc_qsv` in FFmpeg.
- [ ] Public GitHub repository exists with these docs, protected `main`, labels and issue templates.
- [ ] `bench/m0-encode.md`: sustained fps and per-frame encode time for HEVC 2960×1848 @120 on the Iris Xe, plus a 30-minute soak result (throttling yes/no).
- [x] `bench/m0-baseline.md`: Apollo + Artemis glass-to-glass p50/p95 on Wi-Fi (and on USB tethering if available), 20+ samples each. — [`bench/m0-baseline.md`](../../bench/m0-baseline.md). **Deviation accepted by the owner (2026-11-24):** 14 USB / 12 Wi-Fi valid samples, at ~60 fps.
- [x] Tablet facts recorded: Android version, USB tethering present or absent, 120 Hz honoured by Artemis. Android 16 and USB tethering present (#4). 120 Hz was **not** reached with Apollo + Artemis (stream at 51–60 fps, cause not verified), so 120 Hz is split into two open questions: host-side rendering on the virtual monitor (new ARCHITECTURE risk R10, checked in M0-5 and recorded in M0-8) and the tablet side (R7, M1). Accepted by the owner, see #7.
- [ ] AOA-on-Windows path decided in a new ADR (or M2 re-scoped).
- [ ] Go/no-go decision written in this file: native 120 Hz feasible, or the fallback mode M1 will target.
